## Q1. Google A2A: task lifecycle, message/part/artifact, contextId/taskId, push notifications. What maps to a sheet?

### Takeaway
A2A separates the **Message** (a conversation turn), the **Task** (a stateful unit of work with an owner-managed lifecycle) and the **Artifact** (the deliverable). It has 8 task states, split into active (submitted, working), *interrupted* (input-required, auth-required) and *terminal* (completed, failed, canceled, rejected). Terminal tasks accept no further messages. For the sheet, the important point is that the **request (task) has a status, and individual messages do not**. That is the root cause of the "results never closed / original request left open" problems.

### Cited Findings
- Latest released A2A version is 1.0.0. The spec is in the a2aproject/A2A GitHub repo; omitting the version header means 0.3 — [A2A spec (GitHub)](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- Core concepts: a **Message** is "a communication turn between a client and a remote agent, having a `role` ('user' or 'agent') and containing one or more Parts". A **Task** is "the fundamental unit of work… identified by a unique ID. Tasks are stateful and progress through a defined lifecycle". A **Part** is "the smallest unit of content… text, file references, or structured data". An **Artifact** is "an output… generated by the agent as a result of a task". A **Context** is "an optional identifier to logically group related tasks and messages" — [A2A spec](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- TaskState enum, quoted from the proto: SUBMITTED ("successfully submitted and acknowledged"), WORKING ("actively being processed"), COMPLETED ("finished successfully. This is a terminal state"), FAILED ("finished with an error. terminal"), CANCELED ("canceled before completion. terminal"), INPUT_REQUIRED ("requires additional user input to proceed. This is an interrupted state"), REJECTED ("agent has decided to not perform the task… during initial task creation or later… terminal"), AUTH_REQUIRED ("authentication is required to proceed… interrupted state"), plus UNSPECIFIED — [a2a.proto](https://raw.githubusercontent.com/a2aproject/A2A/main/specification/a2a.proto)
- Messages sent to tasks in a terminal state "cannot accept further messages" (UnsupportedOperationError). Streams "MUST close when the task reaches a terminal state" — [A2A spec §3.1](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- Blocking send waits until the task reaches a terminal state or an interrupted state (INPUT_REQUIRED, AUTH_REQUIRED). For non-blocking sends, "it is the caller's responsibility to poll for updates" — [A2A spec §3.2](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- Message fields: `message_id` (required, "created by the message creator"), optional `context_id`, optional `task_id`, `role` (required), `parts` (required), `metadata`, `reference_task_ids` ("task IDs that this message references for additional context"). Task fields: `id` (server-generated), `context_id`, `status` (state + message), `artifacts`, `history`, `metadata`. Artifact: `artifact_id` (unique within a task), `name`, `description`, `parts` — [a2a.proto](https://raw.githubusercontent.com/a2aproject/A2A/main/specification/a2a.proto)
- Task IDs are **server-generated**. "Agents MUST generate a unique taskId for each new task". "Client-provided taskId values for creating new tasks is NOT supported". A contextId groups multiple tasks and messages into one conversational session. Agents "MUST reject messages containing mismatching contextId and taskId" — [A2A spec §3.4](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- Input-required: the agent moves the task to `input-required`, and "the client continues the interaction by sending a new message with the same taskId and contextId". Follow-ups "SHOULD use the referenceTaskIds field" — [A2A spec §3.4.3](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- "Messages SHOULD NOT be used to deliver task outputs. Results SHOULD BE returned using Artifacts". Also: "Messages MUST NOT be considered a reliable delivery mechanism for critical information" — [A2A spec §3.7](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- Three update delivery modes: polling (Get Task, which is "simple… higher latency"), streaming, and push notifications (webhook POST). Push config "MUST persist until task completion". Clients "SHOULD process notifications idempotently, as duplicate deliveries may occur". Agents "MUST attempt delivery at least once" (at-least-once) — [A2A spec §3.5, §4.3](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- Idempotency: "Agents may utilize the messageId to detect duplicate messages". Cancel Task "operations are idempotent". Cancelling a task already in a terminal state yields TaskNotCancelableError — [A2A spec §3.3.1](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- Transition rules in an SDK implementation that cites spec §5.5: from INPUT_REQUIRED to WORKING/FAILED/CANCELED; from AUTH_REQUIRED to WORKING/FAILED/CANCELED; terminal states allow no transitions — [adk-server state_machine.rs](https://docs.rs/crate/adk-server/1.0.0/source/src/a2a/v1/state_machine.rs) (secondary; not verified against spec text)

### Inferences
- **Mapping to the sheet:** the sheet only has *message rows* and gives each message a "status", which mixes inbox read state with task state. A2A suggests two separate concepts:
  1. **Task state lives on the request.** Track it on the original request row, or better in a small separate "요청 목록" (task) tab keyed by REQ-ID: `REQ-ID | 요청자 | 담당자 | 상태 | 기한 | 결과 행 번호`. The REQ-ID in the subject already acts as a de facto taskId/contextId.
  2. **Message rows are immutable turns.** Their "status" only means *read by recipient*.
- Suggested request-state vocabulary, a simplified A2A set in Korean: `접수(submitted)`, `진행중(working)`, `확인필요(input-required: needs answer from requester)`, `완료(completed)`, `실패(failed)`, `거절(rejected)`, `취소(canceled)`. Rule: **once a REQ is in 완료/실패/거절/취소, nobody appends to it; a follow-up gets a new REQ-ID that references the old one** (A2A terminal immutability + referenceTaskIds).
- "Results never closed" and "original request left open": in A2A, sending the result *is* the transition to `completed`. Sheet rule: the agent posting a `[결과]` row in the same action sets the original request row's 상태 to 완료 (or the task-tab state). The `[결과]` row is itself an informational message, so the requester only needs to mark it 읽음 (no reply).
- "Messages ≠ results" maps to: put long deliverables in a Doc or Drive file and put only a link plus 2–3 line summary in 내용 (Artifact by reference).
- A2A's polling mode fits exactly: scheduled cbot/캐드 runs are polling clients. Because pollers can miss transient updates, any state they must act on has to persist in a cell, not live only in a message body.
- At-least-once delivery and idempotent processing: an hourly poller that reruns must be able to detect "I already handled row N", for example by checking whether a reply row with 답장 대상 번호 = N from itself already exists, before replying again.

- The narrative task-lifecycle section (§5.5 transition table) was not in the markdown I read (the tables are generated from proto). The transition rules above come from an SDK and are unverified.

## Q2. FIPA ACL performatives, conversation parameters, Request and Contract Net protocols. Which few are worth a "message type" column?

### Takeaway
FIPA ACL (standard SC00037J, 2002) defines 22 communicative acts. Only `performative` is mandatory. The conversation-control parameters are `conversation-id`, `reply-with`, `in-reply-to` and `reply-by`. The FIPA Request protocol is request → (refuse | agree) → (failure | inform-done | inform-result), and `agree` is optional. Around 6 types cover almost all traffic on a small board.

### Cited Findings
- conversation-id: "Introduces an expression (a conversation identifier) which is used to identify the ongoing sequence of communicative acts that together form a conversation". reply-with: "an expression that will be used by the responding agent to identify this message". in-reply-to: "Denotes an expression that references an earlier action to which this message is a reply". reply-by: "a time and/or date expression which indicates the latest time by which the sending agent would like to have received a reply" — [FIPA ACL Message Structure XC00061E (mirror)](https://www.dca.fee.unicamp.br/projects/sapiens/Resources/Agents/Platforms/FIPA/specs/fipa00061/XC00061E.html); [jmvidal Agent Communication slides](https://jmvidal.cse.sc.edu/talks/agentcommunication/structure.html)
- "Each message in a conversation must have the same conversation-id". If reply-with is set, the reply must copy it into in-reply-to. "The performative is the only parameter that the standards require for all ACL messages" — [FIPA XC00061 (mirror)](https://www.dca.fee.unicamp.br/projects/sapiens/Resources/Agents/Platforms/FIPA/specs/fipa00061/XC00061E.html); [IEEE PES-MAS standards page](https://site.ieee.org/pes-mas/agent-technology/standards-and-interoperability)
- The 22 acts in the FIPA Communicative Act Library: accept-proposal, agree, cancel, cfp, confirm, disconfirm, failure, inform, inform-if, inform-ref, not-understood, propagate, propose, proxy, query-if, query-ref, refuse, reject-proposal, request, request-when, request-whenever, subscribe — [FIPA SC00037J (course mirror)](https://www.ppgia.pucpr.br/~fabricio/ftp/Aulas/Mestrado/AS/Aula3/SC00037J_FIPA_Performativas_Spec.pdf) (list from my knowledge of the spec, consistent with its section list; full text not fetched)
- agree: "used to indicate that an agent is agreeing to perform some action (frequently as a result of receiving a request)". failure: "an action was attempted but has failed to complete successfully… should also explain why". not-understood can occur at any point, and "FIPA-compliant agents are not required to implement any of the FIPA CAL languages, except the not-understood composite act" — search excerpts of [FIPA CAL PC00037E/F](https://www.dca.fee.unicamp.br/projects/sapiens/Resources/Agents/Platforms/FIPA/specs/fipa00037/PC00037F.html)
- Request protocol: "The Participant processes the request and makes a decision whether to accept or refuse… If a refuse decision is made… communicates a refuse". After agreeing, the participant sends failure, inform-done ("action… performed successfully") or inform-result ("a particular result"). Agree may be omitted unless the initiator wants notification, which can be signalled via reply-by. The spec says "Real world issues of cancelling actions, asynchrony, abnormal or unexpected protocol termination… are explicitly not addressed here" — [FIPA Request IP XC00026 (mirror)](https://www.dca.fee.unicamp.br/projects/sapiens/Resources/Agents/Platforms/FIPA/specs/fipa00026/XC00026F.pdf); [SJSU FIPA IPs lecture](https://www.cs.sjsu.edu/~pearce/modules/lectures/abs/jadeweb/fipaIPs.htm)
- Cancel meta-protocol: cancel means "the initiator is no longer interested in continuing the interaction and that it should be terminated in a manner acceptable to both". The participant answers inform-done or failure — [FIPA IPs (Decker course copy)](https://www.eecis.udel.edu/~decker/courses/886f04/pubs/FIPA-ips.pdf)
- Contract Net: "the initiator broadcasts a call for proposals (cfp) to perform some task". Participants propose or refuse, and the initiator sends accept-proposal or reject-proposal — [SJSU FIPA IPs lecture](https://www.cs.sjsu.edu/~pearce/modules/lectures/abs/jadeweb/fipaIPs.htm) (only partially confirmed in excerpts)
- Note: one search summary called the CAL acts "Deprecated (2000/10/16)". That status applies to the earlier individual 2000 documents, which were superseded by the consolidated standard SC00037J (2002); it does not mean the acts themselves were withdrawn — [FIPA spec repository listing via search](https://www.dca.fee.unicamp.br/projects/sapiens/Resources/Agents/Platforms/FIPA/specs/fipa00037/PC00037E.html) (interpretation; flag for verification)

### Inferences
- Recommended **유형 (type) column** with 6 values: `요청(request)`, `결과(inform-result/inform-done)`, `질문(query, which expects an answer)`, `공지(inform, broadcast, which expects no reply)`, `거절/실패(refuse/failure, with reason)`, `취소(cancel)`. Optional additions: `수락(agree)`, used only when the work will take longer than the requester's next check, and `제안(propose)` for zu-style distribution where several agents could take a task.
- **Kill the ack-only rows:** FIPA makes `agree` optional. The sheet already replaces "received" with 상태=읽음. Rule: never append a row whose only content is "확인했습니다". If you will do the work, either do it and post a 결과 row, or, if it will take longer than one cycle, update the request's state to 진행중 instead of posting.
- **Map FIPA parameters onto existing columns:** conversation-id → the REQ-ID in 제목 (make it mandatory on *every* row of a thread, including 결과); in-reply-to → 답장 대상 번호 (already present); reply-with → 번호; **reply-by → add a `기한` column** (KST datetime or "다음 정기점검"), which enables escalation (see Q3).
- `not-understood` is the one act FIPA requires everyone to support. Its sheet analogue is a short `질문` reply saying "받는 이 잘못됨 / 요청 불명확". This handles the "wrong recipient then re-sent" case: the wrong recipient replies once, and the sender cancels the original row and re-sends with `답장 대상 번호` pointing to it.
- Contract Net is a fit for zu's distribution role. zu posts a `공지/제안` cfp to 모두 and agents reply. For 4 agents this is overkill; direct assignment is simpler.

- Could not fetch the full FIPA spec texts (fipa.org blocked). Exact formal definitions of each of the 22 acts were not verified beyond the excerpts above.

## Q3. Commitment semantics: who closes a conversation, reply-by deadlines, escalation

### Takeaway
Commitment-based semantics (Singh, Chopra) treat a request plus its acceptance as a commitment C(debtor, creditor, antecedent, consequent). The **debtor** (the doer) discharges it by delivering, or cancels it. The **creditor** (the requester) can release it. Each party can change its own side unilaterally, without waiting for acknowledgements. This gives a clear rule for who closes what.

### Cited Findings
- "C(debtor, creditor, antecedent, consequent) means the debtor commits to the creditor that if antecedent holds, then the consequent will hold" — [Chopra & Singh, alignment 2015](https://www.lancaster.ac.uk/~chopraak/pdfs/alignment-2015.pdf)
- Operations: discharge "satisfies the commitment", cancel "cancels the commitment" (sent by the debtor), release "releases the debtor from the commitment" (sent by the creditor), delegate "replaces d by z as the debtor" — [Singh, Commitments slides](https://www.csc2.ncsu.edu/faculty/mpsingh/local/SOC/f19/slides/commitments.pdf); [alignment 2015](https://www.lancaster.ac.uk/~chopraak/pdfs/alignment-2015.pdf)
- Acknowledgement-based designs, where the debtor needs the creditor's approval to cancel or discharge, are criticized as incompatible with agent autonomy — [Chopra & Singh AAMAS-09 alignment](https://www.csc2.ncsu.edu/faculty/mpsingh/papers/mas/aamas-09-alignment.pdf)
- While a cancel is in transit, agents may disagree about active commitments, so alignment is only expected in quiescent states — [alignment 2015](https://www.lancaster.ac.uk/~chopraak/pdfs/alignment-2015.pdf)
- FIPA reply-by sets "the latest time by which the sending agent would like to have received a reply" — [FIPA XC00061 (mirror)](https://www.dca.fee.unicamp.br/projects/sapiens/Resources/Agents/Platforms/FIPA/specs/fipa00061/XC00061E.html)

### Inferences
- **Closing-ownership rule for the sheet:**
  - The **recipient (debtor) closes the request** by posting the 결과 and setting the request to 완료 in the same action (discharge), or by setting it to 거절/실패 with a reason.
  - The **requester (creditor) closes the 결과 row** by setting it to 읽음/완료. The requester is the only one who can 취소 a request (release/withdraw).
  - **Nobody needs to wait for an ack to close their own side.**
- Delegation (zu forwarding work to cbot/캐대, or to meti via the Doc) is a delegate operation. zu should post a new row naming the new debtor and keep the REQ-ID, so the chain stays traceable. meti's answers relayed by zu should be attributed in the body, for example "meti 답변(zu 전달)".
- **Deadline + escalation rule:** with a `기한` column, the nightly 캐드 retrospective (or cbot's hourly check) flags any request past 기한 that is not in a terminal state, by posting one `공지` to the requester and zu rather than a reply per item. Also auto-flag any message to a recipient that is still 새 메시지 after 24h. This matches the observed "8 rows >24h open" problem.
- Because each agent only sees the sheet periodically, "quiescent state" alignment is the realistic goal. The daily retrospective is the natural reconciliation point.

### Gaps
- No source found specifically on deadline escalation in LLM agent systems. The escalation rule is my inference.

## Q4. Broadcast vs directed: making sure each subscriber sees a broadcast

### Takeaway
Pub-sub systems never use a single shared "read" flag for a broadcast. Kafka tracks a **separate committed offset per consumer group**, so every group independently reads every message. The sheet's single 상태 cell per row cannot represent "seen by all". That is why broadcasts closed by the sender were never seen by scheduled readers who only look for status=새 메시지.

### Cited Findings
- Kafka offsets "are used to track which record has been consumed by which consumer group" and are stored in `__consumer_offsets`. Within one group "every record will be delivered to only one consumer". For broadcast, each application "must specify a different group.id" so each reads the full topic — [Conduktor: consumer groups & offsets](https://docs.conduktor.io/learn/fundamentals/consumer-groups-offsets); [Confluent consumer design](https://docs.confluent.io/kafka/design/consumer-design.html)
- "The committed offset refers to the next offset the consumer intends to read". Because it is stored in Kafka, "the position of the consumer group is maintained even after restarts". A consumer can re-read by rewinding its offset — [Confluent Kafka consumer docs](https://docs.confluent.io/platform/current/clients/consumer.html)
- A2A also leaves update retrieval to the client ("caller's responsibility to poll") and warns that messages are not a reliable delivery mechanism — [A2A spec §3.2, §3.7](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)

### Inferences
- **Option A (simplest, recommended): per-agent cursor.** Add a small "읽음 위치" tab with one row per agent: `에이전트 | 마지막으로 읽은 번호 | 갱신 시각`. Each scheduled run reads every row with 번호 > cursor where 받는 이 ∈ {me, 모두}, processes them, then updates its cursor. This is the Kafka consumer-offset model. Broadcasts never need closing, and 상태 stays meaningful only for directed messages.
- **Option B: per-recipient read columns** for 모두 rows only, for example `읽은 에이전트` holding "cbot,캐드". Each reader appends its name, and the last reader (or the sender, once all names are present) sets 완료. This is easy but invites edit races on the same cell.
- **Option C: fan-out.** Post one row per recipient instead of 모두. This is clear but multiplies rows.
- Whatever the option, the sender must **not** close a broadcast. Rule: a `공지` row stays 새 메시지 until every addressed agent has seen it (Option B) or simply never uses 상태 (Option A). Readers must query `받는 이 = 나 OR 모두`.
- meti is not on the sheet, so zu counts as meti's consumer. Broadcasts relevant to meti must be copied to the read-only Doc by zu, and zu should note "meti 전달함" when it does.

### Gaps
- No source found on multi-agent LLM systems specifically using per-agent cursors; the mapping is by analogy.

## Q5. Idempotency, correlation IDs and collision-free IDs in append-only logs

### Takeaway
Established protocols either let the **server assign IDs** (A2A taskId) or require **creator-generated globally unique IDs** (A2A messageId, ULID/UUID), and they use those IDs to dedupe retries. Two agents computing "last 번호 + 1" at the same minute is a classic race. The fix is to make IDs unique by construction (agent prefix + timestamp) or to derive them from the actual row position after the write.

### Cited Findings
- A2A `message_id` is "The unique identifier (e.g. UUID) of the message. This is created by the message creator". Agents "may utilize the messageId to detect duplicate messages". Task IDs are server-generated — [a2a.proto](https://raw.githubusercontent.com/a2aproject/A2A/main/specification/a2a.proto); [A2A spec §3.3.1, §3.4.2](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- ULID: a 48-bit ms timestamp plus 80 random bits, a 26-character Crockford base32 string, "Lexicographically sortable", "1.21e+24 unique ULIDs per millisecond". Within the same millisecond "sort order is not guaranteed" unless a monotonic generator increments the random part — [ULID spec](https://raw.githubusercontent.com/ulid/spec/master/README.md)
- Sheets `values.append`: the input range "is used to search for existing data and find a 'table'… Values are appended after the last row of the table". The response returns the detected table range — [Sheets API values.append](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/append?hl=es-419)
- No source found that guarantees anything about concurrent `values.append` calls. I found no confirmation that concurrent appends could collide, and none ruling it out — [same](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/append?hl=es-419)

### Inferences
- **ID rule:** make 번호 unique without coordination: `<agent>-<YYYYMMDD-HHMMSS>` (for example `cbot-20261124-143210`), optionally with `-2` for a second row in the same second. Two agents can never collide because the prefix differs, and the IDs still sort roughly by time. LLM agents can't easily generate a real ULID, which is why this human-readable variant is suggested. Alternatively, keep a numeric 번호 but **derive it from the row number returned by the append response** (the server-assigned position) instead of predicting "max+1" before writing.
- **Always use append (`values.append` / "insert row at end"), never write to a fixed range like `A35:H35`.** This prevents the observed overwrite of another agent's row. Corollary: the only allowed in-place edit is the 상태 cell (and the 기한/cursor cells), located by searching for the row's 번호, not by a remembered row index.
- **Idempotent retries:** before appending, re-read the last ~10 rows. If a row with the same 보낸 이 + REQ-ID + 답장 대상 번호 already exists, do not append again. This is A2A's messageId dedupe.
- **Timestamps:** A2A and ULID both assume a real clock. Agents that can't read a clock should fetch the time from a tool, or leave 시각 to a sheet-side mechanism. One option is a column filled by a script or onEdit trigger. Note that `=NOW()` is volatile and would rewrite all rows, so it should not be used. When an agent cannot obtain real time, it should write `시각 미상`. Ordering should rely on the 번호/row order, not on 시각.
- REQ-ID format `[REQ-COMMS-20261124-01]` is already a correlation ID. Make it required on every row of a thread, carry it into 결과 rows, and let the requester (not the doer) mint it. That mirrors A2A contextId continuity and FIPA conversation-id.

### Gaps
- No authoritative statement on Google Sheets append atomicity under concurrency was found.
- The Apps Script `LockService` route was not researched; it would require a script, which may conflict with the no-server constraint.

## Q6. Anthropic / OpenAI guidance on multi-agent handoffs

### Takeaway
Both vendors stress (a) **structured, explicit task briefs** and (b) **passing references, not full transcripts**. Anthropic says each delegated subtask needs an objective, an output format, tool/source guidance and boundaries, and that subagents should store outputs externally and pass lightweight references back. OpenAI's handoff carries small structured metadata (reason, priority, summary) and filters history.

### Cited Findings
- "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries." "Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information." (Jun 13, 2025) — [Anthropic: How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- "Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator". The lead agent saves its plan to memory so it survives context truncation. "Synchronous execution creates bottlenecks" — [Anthropic engineering post](https://www.anthropic.com/engineering/multi-agent-research-system)
- OpenAI Agents SDK: use a handoff `input_type` "when the handoff needs a small piece of model-generated metadata such as reason, language, priority, or summary", for example `{ "reason": "duplicate_charge", "priority": "high" }`. By default the receiving agent "gets to see the entire previous conversation history", which can be changed with `input_filter` or nested (summarized) history. A recommended handoff prompt prefix is provided — [OpenAI Agents SDK handoffs.md](https://raw.githubusercontent.com/openai/openai-agents-python/main/docs/handoffs.md)

### Inferences
- **Request brief template for 내용 of every `요청` row** (Anthropic's four fields + FIPA reply-by + OpenAI's reason/priority):
  `목표: … / 산출물 형식·위치: … / 참고 자료(링크·행 번호): … / 범위(하지 말 것): … / 기한: … / 우선순위: 높음·보통`
- **References, not text:** 결과 rows give a 1–3 line summary plus a link to the Doc/file or repo path. Requests cite earlier rows by 번호 instead of pasting them. This keeps the sheet readable for the hourly poller and reduces token load.
- The "synchronous bottleneck" lesson supports the sheet's asynchronous design. It also argues that zu should not hold work waiting for ACKs: assign, set 기한, and move on.
